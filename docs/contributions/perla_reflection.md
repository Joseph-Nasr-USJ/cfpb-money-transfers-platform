# Perla Boustany - Individual Reflection

My main responsibility in this project was the analytics and visualisation layer. I worked on defining the analytical measures, implementing the Q1 to Q5 analyses, developing the Streamlit dashboard, interpreting the two Spark MLlib analyses, and documenting the results. This role required me to connect several parts of the project rather than treating the dashboard as an isolated interface. The figures shown to the user had to agree with the MongoDB serving layer, the analytical scripts, the project definitions and the final report.

One of the most important things I learned was the value of defining measures before building charts. For example, terms such as timely-response rate, processing lag, fraud-or-scam share and share of complaints can easily be interpreted incorrectly if their denominator is not fixed. Writing the metrics definitions first made the later analysis more consistent. It also helped me understand why this project had to remain descriptive and diagnostic. A high complaint share does not mean a company has poor service, and an increase in complaints does not prove an increase in product usage or harm.

The dashboard was another useful part of the project because it required both technical and communication decisions. I used shared filters so that the same date, sub-product, issue, state, submission-channel and company selections could be applied consistently across pages. The dashboard reads from MongoDB rather than directly from the raw or curated files. Redis is used as a cache-aside layer with a fixed time-to-live, while MongoDB remains the source used for analytical queries. I also had to consider failure cases such as empty selections, invalid ranges, missing categories and database unavailability. These details made the dashboard more reliable and showed me that visualisation work includes error handling and data interpretation, not only chart design.

The machine-learning part was particularly useful because the correct result was not necessarily an exciting one. For emerging issues, the pre-declared Linear Regression rule required a sufficiently positive monthly-share slope, an R-squared threshold and a minimum number of complaints. None of the evaluated models satisfied all conditions. Instead of changing the thresholds to obtain a positive result, I reported that no issue qualified. This reinforced the importance of defining a rule before looking at the outcome. The state-segmentation analysis used KMeans and selected the best value of k using the silhouette score. I learned to explain both analyses as pattern-description tools rather than predictive models.

Another challenge was reproducibility. My MongoDB database contained 205,500 complaints when I executed the analytics because scheduled API runs had already added records after the reference full load. The team's documented 24 Nov full load contained 205,271 complaints. This difference showed how important it is to record the exact analytical snapshot used for percentages and counts. I updated the documentation so the reference full load and my fixed analytical snapshot are clearly distinguished.

Git collaboration also became an important part of my work. I used separate commits for meaningful tasks, merged updated main changes into my branch, removed generated CSV outputs from tracking, responded to review feedback and kept the PR focused on the analytics deliverables. Review comments helped identify issues that were easy to miss locally, including ambiguous snapshot wording and file encoding.

Overall, this project improved my understanding of how analytics fits into a complete data platform. I became more careful about denominators, reproducibility, limitations, caching, database integration and responsible interpretation. For the final demonstration, my goal is to explain Q1 and Q2 clearly from the dashboard while also being able to justify the methods, the snapshot used and the limitations behind every result.
